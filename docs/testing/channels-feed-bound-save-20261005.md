## 证据

- 截图中的 `173602` / `173236` 匿名 MSE 文件完全相同，实际仅约6.20秒，画面为机器人短片，并非用户指定的回放。仅能证明缓存被保存，不能据此声称回放完整下载。
- 当前播放器没有匹配的 blob/MSE 链时，旧代码会选择唯一剩下的旧链。最小回归复现了“当前长回放保存成旧短片”。
- 即使 `sourceended`，6秒播放器窗口也不能证明原片只有6秒。两个回归复现了匿名6秒、23秒原视频仅缓存6秒仍被提交成功的问题。
- 同一 Feed 的解密参数迟到时，首次能力视图不刷新；旧请求迟到也会覆盖新视图。两种回调顺序都已覆盖回归。

## 修复

1. 当前视频必须经自身 blob URL 匹配 MSE 链，删除“唯一旧链”的回退；复用 video DOM 时也不能把旧缓存重命名为新视频。首次观察时身份未知的旧链也不能用切换后出现的 Feed 补绑定。
2. 捕获链冻结真实 Feed ID，并按 Feed 的 `videoPlayLen` 与已观察时长的最大值核对各轨完整覆盖。没有原片身份/时长时不提交成功。
3. MSE end 上传 Feed ID。后端再次查询原 Feed、全轨解码并核对真实时长，成功复用原标题、作者和 ID，不再制造匿名成功条目。直接下载已完成时复用其文件，避免重复统计和保存。
4. FeedStore 补全后续捕获的时长等元数据；已知完整时长不被短预览降低。校验期间迟到更长时长时，发布前再次校验。
5. 能力视图随新参数更新，按捕获版本丢弃过时响应，使按钮能够使用完整源文件下载任务。
