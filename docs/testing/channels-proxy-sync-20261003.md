# 视频号 Windows 代理同步修复（2026-10-03）

## 真实故障与证据

微信 4.1.15.13 已打开视频号，下载器会话运行、根证书受信任，但
`target_domain_connections=0`、`feeds_total=0`。代理的普通 TCP 连接超过
100 次，均不能证明微信流量经过下载器。

用户彻底退出并重开微信后，`WeChatAppEx.exe` 的网络服务进程连接
`127.0.0.1:7897`（Clash），下载器却监听 `127.0.0.1:8899`。
顶层注册表 `Internet Settings\ProxyServer` 已是 `8899`，而
`Connections\DefaultConnectionSettings` 与 `SavedLegacySettings` 仍是
`7897`。通过 `InternetQueryOptionW(75)` 只读查询实际 LAN 代理，结果同为
`7897`。原实现只写顶层注册表，未同步客户端实际读取的连接选项。

## 本次修改

- 通过 `InternetSetOptionW(75)` 同步 LAN 代理；设置前备份恢复记录，停止时
  恢复原始代理、PAC 标志、顶层字段与两份连接二进制值。设置/通知失败保留
  恢复能力，正常停止和异常恢复都保护用户后续手动改动。
- 后台缓存式只读检查微信进程与 TCP 所属 PID；状态接口和界面显示真实微信
  连接证据与有效代理不一致，避免把浏览器连接当微信已接入。
- CONNECT、SNI、HTTP Host 识别按连接去重；TLS 成功/失败分别计数。
  域名摘要有界，不包含路径、查询参数、请求正文。
- 已确认含 `objectDesc` 的视频数据支持 `objectId` / `id` / `nonce` 标识，
  保留长整数的字符串精度；修正运行时捕获的策略归属。

## 验证

修复前在线复现检查：`proxy>100`、`target=0`、`feeds=0`，断言失败。
离线故障回归先红后绿。视频号后端全套 372 项通过；随后新增代理恢复边界
测试，代理/连接/状态的最终组合 37 项通过（含全部 26 项代理恢复测试）。
前端全套 77 项通过；本次相关 Python 文件 Ruff 与 diff 空白检查通过。

以上仅证明源码与离线恢复逻辑。实际系统设置同步、微信真实捕获、落盘媒体的
完整性验收，须在用户授权系统配置及外部恢复记录写入后继续。

## 用户补充：视频号不使用 Clash

普通视频、图片、封面、BGM 的 aiohttp 会话明确 `trust_env=False`，媒体请求
不使用项目通用代理配置，也不继承 `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY`。
直播 FFmpeg 仅在其子进程环境中去掉这些变量（大小写均覆盖），其他环境保留，
父进程和系统环境不变。已有 Wi-Fi 默认路由，无活跃 Clash 虚拟网卡证据。
这些源码设置已离线验证，仍须重启项目服务及获授权同步本机连接代理后生效。

## 本机实际验收（已完成）

用户要求继续重试后，按之前说明的临时系统代理及恢复记录范围执行。先停止旧
嗅探会话，确认没有正在下载的任务，再重启项目服务并启动新捕获。只读检查
顶层注册表与 `InternetQueryOptionW(75)` 均返回 `127.0.0.1:8899`。
用户重开微信并播放后，微信进程 TCP 连接实际进入 `8899`：目标域 8 次，
客户端 TLS 成功 8 次、失败 0 次，页面注入/按钮/心跳正常。

实际捕获和保存 2 个 MSE 视频，统计成功 2、失败 0：一条 6 秒视频与一条
241 秒视频。长片输出 177,063,638 字节；用 FFmpeg 分别完整解码视频和音频，
两轨均退出 0，测得视频 240.700 秒、音频 240.605 秒，与捕获目标时长一致。
验收结果见项目 `.verify/channels-real-download-validation.json`；文件位于
`Downloaded/视频号作者/channels/` 下，本机捕获会话保持运行供用户继续下载。
本轮没有实机停止新会话，以保留当前捕获列表；停止恢复已有 26 项离线代理
同步/回滚/精确恢复测试覆盖。
